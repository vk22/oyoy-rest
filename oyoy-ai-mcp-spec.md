# OyOy Restaurant: доступность для ИИ-поиска и MCP-ассистентов

Техническое задание для Claude Code · 25 октября 2026

## 1. Задача

Работай в существующем репозитории сайта https://oyoyrestaurant.com/.
Реализуй минимальную работающую версию, которая:

1. Делает сведения о ресторане и меню доступными в HTML без выполнения JavaScript.
2. Использует единый источник данных для страниц, структурированной разметки и MCP.
3. Позволяет подключённому MCP-клиенту получить сведения о ресторане, найти блюда и получить ссылку бронирования.
4. Сохраняет текущий дизайн, навигацию и работающий сценарий бронирования через TheFork.

Результат — изменения в коде, проверки и инструкция подключения. Создание отдельного чат-бота на сайте не требуется. Публикация MCP не означает автоматического подключения ко всем ИИ-ассистентам и не гарантирует рекомендации ресторана.

## 4. Единый источник данных

Создай типизированный слой доступа к данным, независимый от HTTP и MCP. Страницы, REST API и MCP вызывают одни и те же функции и получают согласованные данные.

Если CMS/БД уже содержит меню — используй её, не создавай вторую ручную копию. Если меню существует только в PDF/картинках — подготовь редактируемый структурированный источник. Извлечённые цены и состав требуют сверки; неподтверждённые записи не публикуются. Если CMS отсутствует, для пилота достаточно валидируемого JSON/TS-файла; новую БД и редактор меню не строить.

### Restaurant

- id, name, description, canonicalUrl;
- address, geo (только проверенные координаты), telephone, email;
- timezone: Europe/Malta;
- cuisines, currency: EUR;
- weeklyOpeningHours и specialOpeningHours для исключений;
- features: только подтверждённые свойства, например terrace или seaView;
- bookingUrl, socialLinks;
- updatedAt — время изменения содержимого, не текущий момент запроса;
- отдельные признаки достоверности для полей, если нужны для фильтрации публикации.

Не смешивай часы работы ресторана, кухни и доступные слоты бронирования. Часы работы не являются подтверждением наличия столиков. Для неизвестного расписания возвращай null/unknown; это не означает «закрыто».

### Menu и MenuItem

- Меню: id, title, language, currency, updatedAt, список категорий и позиций.
- Позиция: id, categoryId, name, description, price, pricingType, unit, status, sourceUrl.
- pricingType: fixed, from, market или unknown. price — число или null.
- status: published, unavailable или draft. Смысл unavailable — блюдо не предлагается, а не статус наличия столиков.
- При необходимости: варианты порций, количество в порции и единицы цены.
- dietaryTags и allergens — только подтверждённые, с возможностью unknown.

Не выводи «без глютена», «без орехов» и другие гарантии из названия блюда или неполного описания. Отсутствующий аллерген в данных не означает его отсутствие в блюде. Не превращай цену за 100 г или одну штуку в цену за полную порцию.

## 5. Публичные страницы и поиск

### /menu

Сделай отдельную страницу меню в дизайне проекта:

- SSR-HTML содержит категории, названия, описания, цены, EUR и единицы измерения;
- страница читается без JavaScript, без обязательного согласия на cookies;
- корректно показывает цены from/market/unknown и недоступные блюда;
- имеет понятные заголовки, title, description, canonical и доступные ссылки;
- PDF, если он используется, остаётся дополнительной ссылкой;
- на главной добавлена обычная ссылка на /menu; существующие якоря не ломаются;
- даты актуализации отображаются только при наличии реальной даты.

Винную карту интегрируй аналогично только если доступны структурированные данные; её полная оцифровка не блокирует основной пилот.

### Сведения о ресторане

Добавь проверенное расписание и полезные сведения в существующий блок контактов или подходящую существующую страницу. Не создавай неподтверждённые ответы про детей, парковку, доступность, дресс-код и диеты.

### JSON-LD

Добавь серверную разметку schema.org Restaurant со стабильным @id, например https://oyoyrestaurant.com/#restaurant.

Поля: name, url, description, telephone, address, image, servesCuisine, geo, sameAs, openingHoursSpecification и specialOpeningHoursSpecification — только при наличии достоверных данных. hasMenu должен вести на /menu; acceptsReservations — на существующую /reservations.

Меню можно описать через Menu → MenuSection → MenuItem → Offer для цен, которые действительно представлены на странице. Не выдумывать Offer с нулевой ценой для market/unknown. Разметка должна соответствовать видимому контенту, быть безопасно сериализована и не дублировать конфликтующие сущности. Не добавляй aggregateRating по неподтверждённым отзывам. JSON-LD описывает данные и не создаёт интеграцию бронирования.

### Индексация

- Проверь robots, meta robots и sitemap: /menu индексируется и включена в sitemap.
- Сохрани ограничения для административных страниц. robots.txt не заменяет авторизацию.
- Проверь HTTP-статусы, canonical, редиректы и доступность основных данных в исходном HTML.
- Не добавляй /api и /mcp в sitemap.
- llms.txt не входит в обязательный объём: он не заменяет HTML, данные или подключение MCP.

## 6. Публичный API

Реализуй минимальные read-only маршруты либо используй подходящие существующие:

| Маршрут | Назначение |
| --- | --- |
| GET /api/public/restaurant | Сведения о ресторане и ссылка бронирования |
| GET /api/public/menu | Опубликованное меню; фильтры query, category, maxPrice, limit |

Имена можно адаптировать к проекту, зафиксировав итоговый контракт. Не создавать дубликаты существующего API.

Ответы должны иметь единый формат данных, sourceUrl и updatedAt. API не отдаёт черновики, служебные поля, персональные данные и ключи интеграций. Валидируй входные значения; limit по умолчанию 20, максимум 50, query максимум 200 символов, maxPrice — конечное неотрицательное число. Неизвестный фильтр категории — документированная ошибка, а не произвольный ответ. Пустой поиск — успешный пустой результат.

Поиск и фильтрация работают детерминированно без вызовов LLM. Для пилота достаточно нормализации регистра и поиска по названию, описанию, категории. Не добавляй отдельный AI API или векторную БД. maxPrice фильтрует только фиксированные цены сопоставимых позиций; from/market/unknown и неоднозначные единицы не должны выдавать ложное обещание уложиться в бюджет. Правила исключений явно документировать.

## 7. MCP-сервер

Реализуй удалённый endpoint /mcp на официальном TypeScript SDK с транспортом Streamable HTTP. Перед реализацией проверь текущую стабильную версию и официальные инструкции SDK. Закрепи совместимые зависимости и lockfile. Не копируй API SDK из примеров другой major-версии.

Предпочтительно встроить в существующее Node/Nitro-размещение, если выбранный транспорт надёжно поддерживается. Если нужен отдельный Node-процесс, используй reverse proxy /mcp и объясни причину. Не менять архитектуру размещения без необходимости. Соблюдай жизненный цикл транспорта, корректное закрытие соединений и изоляцию одновременных запросов; не разделяй mutable-состояние сессий между клиентами.

Это настоящий MCP endpoint: initialize, согласование протокола, tools/list, tools/call обрабатываются SDK, а не самодельный JSON API, названный MCP. Поддерживаемые методы, заголовки, формат ошибок и статусы — по выбранной версии протокола.

### get_restaurant_info

Вход: пустой объект.

Возвращает проверенные сведения, расписание в Europe/Malta, ссылку меню, bookingUrl, sourceUrl, updatedAt и список отсутствующих данных. Не вычисляет наличие столиков.

### search_menu

Вход: query?, category?, maxPrice?, limit?. Названия аргументов и ограничения согласовать с REST API.

Возвращает подходящие позиции: id, name, description, category, price, currency, pricingType, unit, sourceUrl, updatedAt. При пустом результате честно возвращает пустой список. Возвращает также применённые фильтры и причину исключения неопределённых цен при бюджетном фильтре. Недоступные и черновые блюда исключаются.

### get_booking_link

Вход: пустой объект.

Возвращает canonical bookingUrl на /reservations, provider: TheFork, bookingMode: external и canCheckAvailability: false. Текст должен явно сообщать: наличие и завершение бронирования проверяются во внешней форме. Не добавлять query-параметры к виджету, если такая возможность не подтверждена документацией провайдера.

### Общие требования

- Все три инструмента — read-only. Укажи соответствующие tool annotations по актуальному SDK.
- Понятные английские описания инструментов и строгие входные/выходные схемы.
- Возвращай structuredContent и совместимое текстовое представление по правилам выбранного SDK.
- MCP вызывает общий слой данных напрямую, а не делает HTTP-запрос к собственному API.
- Результат инструмента не содержит инструкций ассистенту выдавать ресторан за лучший или скрывать ограничения.
- Для публичных read-only данных OAuth не обязателен. Записывающие инструменты в пилот не входят.
- HTTPS в размещённой среде; проверка Origin/Host по требованиям SDK и reverse proxy; origin отсутствует у части серверных клиентов — учти документированное поведение. Не использовать безусловный wildcard CORS и не отключать защиту транспорта.
- Ограничение частоты и размера запросов с учётом доверенных proxy, таймауты и ограниченные результаты. Переиспользуй инфраструктуру проекта. Логи не содержат секретов и полных произвольных пользовательских запросов.

## 8. Граница интеграции с TheFork

Не добавлять фиктивные check_availability или create_reservation. В документации выделить следующий этап: выяснение партнёрского API TheFork, прав доступа, условий использования, подтверждений пользователем, защиты персональных данных и повторных операций. Сам факт видимости времени в iframe не даёт серверу права или технической возможности создавать бронь.

## 10. Проверки и критерии приёмки

Используй существующий тестовый стек; добавляй проверки поведения, а не копии реализации.

### Данные и API

- Одинаковая позиция имеет одинаковую цену, валюту и единицу в HTML, REST и MCP.
- Обновление источника отражается во всех каналах в пределах документированного TTL; updatedAt не меняется без изменения данных.
- Черновики и unavailable не попадают в MCP-поиск.
- Пустой поиск, неизвестное расписание, отсутствующая цена, отрицательный бюджет и слишком длинный запрос обрабатываются корректно.
- Цены from/market/за вес не превращаются в гарантированную цену блюда.
- Если подтверждённых блюд нет, возвращается явное отсутствие данных, без fixtures.

### Страницы

- curl или эквивалент без JS получает фактические блюда и цены на /menu, если такие данные предоставлены.
- JSON-LD синтаксически валиден и соответствует контенту; URL, canonical и sitemap корректны.
- Проведена визуальная проверка /menu, главной и /reservations на мобильной и настольной ширине.
- Текущий iframe TheFork, якоря главной и навигация продолжают работать.

### MCP

- Реальный SDK-клиент выполняет initialize, tools/list и tools/call для всех трёх инструментов через HTTP, а не прямой вызов обработчиков.
- Неверные параметры отклоняются; пустой поиск возвращает пустой результат.
- Проверены параллельные вызовы, неизвестный инструмент и завершение соединений.
- При имитации TheFork или недоступности внешнего сайта не появляется подтверждение брони.
- Через MCP Inspector проверены схемы и реальные ответы.
- Если совместимый ИИ-клиент доступен, выполнить три сценария ниже; если нет — честно указать, что проверен протокол, а разговорный сценарий пока не проверен.

### Разговорные сценарии

1. «Где находится OyOy и когда работает?» → достоверный адрес и расписание либо явное указание, что часы не подтверждены.
2. «Какие блюда с морепродуктами есть до €25?» → реальные совпадения с корректными ценами или честное отсутствие результатов; не гарантировать полноту свободного текстового поиска.
3. «Забронируй столик на завтра на троих» → ссылка на /reservations и объяснение, что бронь необходимо завершить в TheFork; никаких вымышленных слотов и номеров подтверждения.

Запусти применимые lint/typecheck/build и содержательные тесты. Отдельно перечисли пропущенные проверки с причиной. Отсутствие подтверждённых данных не выдавай за завершённую готовность к production: обозначь конкретные блокирующие поля.
